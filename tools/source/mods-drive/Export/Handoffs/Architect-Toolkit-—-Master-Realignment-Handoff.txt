## Purpose

This handoff captures the current realigned direction for **Architect Toolkit for Enshrouded**.

It combines:

* the current Architect development state;
* the existing creative-feature vision;
* the newest UX/layout decisions;
* the newly available unpacked Enshrouded KFC resource evidence in Google Drive;
* the decision to favor extending/composing vanilla Enshrouded systems over rebuilding equivalent systems from scratch;
* the project’s evidence-first reverse-engineering and native-safety rules.

This document is a **continuity and planning guide**, not proof that every feature described below exists.

Current source code, logs, captures, tests, KFC evidence, and user-confirmed in-game behavior always override planning text.

---

# 1. PRIMARY OPERATING RULES

For all Enshrouded work, consult and apply:

**ENshrouded Mod Development GPT — Core Instructions**

Treat it as the primary development guide.

Always distinguish:

**PROVEN**
Supported by runtime evidence, tests, captures, or user-confirmed behavior.

**INFERRED**
Strongly suggested by evidence but not fully validated.

**EXPERIMENTAL**
Currently under active testing.

**UNSOLVED**
Mechanism is not yet known.

**PLANNED**
An intended feature or architecture.

**SPECULATIVE**
A worthwhile possibility that has not yet been established technically.

Never promote a feature or mechanism to PROVEN merely because it compiles, appears plausible, exists in planning, or resembles another Enshrouded system.

Use:

**observe → capture → map → validate → minimally modify → verify**

Do not invent Enshrouded APIs, fields, structures, offsets, resource semantics, calling conventions, or runtime behavior.

# 4. KNOWN HIGH-RISK / DISPROVEN NATIVE DIRECTIONS

Preserve the lessons from previous native research.

Do **not** casually revive previously rejected global resolver/function-entry/selector hooks merely because a new feature needs placement control.

A previous selector trampoline crashed because register state was corrupted when the trampoline used RAX as a resume address after copied instructions had established meaningful RAX state.

The important lesson is broader than that one crash:

**hook placement and complete machine-state preservation matter.**

Previously rejected or dangerous interception sites must stay disabled until separately reviewed against current source/build evidence.

Unsafe mutations must fail closed.

Use:

**build fingerprint → signature validation → sanity checks → install → validate → clean uninstall**

For world-changing experiments, use a test world.

# 5. MAJOR PROJECT REALIGNMENT

The central development philosophy has changed.

Old tendency:

**Architect reimplements the feature itself.**

New preferred approach:

**Architect finds the closest vanilla Enshrouded system and extends, composes, or orchestrates it.**

The order of preference is now:

**REUSE → EXTEND → COMPOSE → AUGMENT → REPLACE**

Before building any significant feature from scratch, ask:

> What existing Enshrouded system already performs the closest equivalent operation?

If a vanilla mechanism already provides:

* placement;
* snapping;
* preview;
* transforms;
* world mutation;
* inventory semantics;
* map display;
* camera behavior;
* terrain interaction;
* entity placement;
* multiplayer authority;
* validation;
* persistence;

then Architect should attempt to use that mechanism rather than implementing a parallel substitute.

Architect should provide the **better workflow and intelligence**.

Enshrouded should remain the **host engine whenever practical**.

# 7. VANILLA ADAPTER ARCHITECTURE

Plan for common adapters such as:

### Build Adapter

Potential responsibilities:

* vanilla blueprint selection;
* blueprint geometry;
* snapping;
* preview;
* orientation;

### Terrain Adapter

Use Enshrouded's existing terraforming/world-voxel mechanisms where possible.

Architect adds:

* brush shapes;
* radius;
* falloff;
* paths;
* grading;
* repetition;
* preview;
* transactions.

### Entity / Decoration Adapter

Use vanilla entity/template/scene placement semantics where they can be identified.

This should eventually support:

* furniture;
* decoration;
* foliage;
* lighting;
* repeated entities;
* scatter systems.

### Inventory Adapter

Prefer semantic game-owned inventory operations over arbitrary memory editing.

### Map Adapter

Reuse vanilla map/marker/fast-travel display behavior where possible.

### Camera Adapter

Investigate existing camera states and overrides before implementing a separate camera controller.

### Movement Adapter

Investigate existing movement/airborne/glider/traversal systems before falling back to raw transform manipulation.

### Water Adapter

Water remains research-heavy.

The KFC library contains multiple explicit water resource families, but programmatic creative water editing remains unproven until mapped.

# 8. CREATIVE PHILOSOPHY

Architect Toolkit should **enable creativity rather than replace creativity**.

Primary principle:

> Give the player better tools to create what they imagine instead of making the creative decisions for them.

Architect should generally:

* suggest;
* preview;
* guide;
* measure;
* align;
* organize;
* simplify repetition;
* expose useful options.

Architect should generally **not** automatically decide what the player's building, garden, room, roof, lighting scheme, or design should be.

A major rule:

> If Architect would make a creative decision for the player, prefer suggestions and previews.

> If Architect merely removes repetitive labor after the player has defined the rules, automation is appropriate.

Examples:

Smart Roof Solver → suggest/preview.

Interior Designer → suggest/preview.

Material Harmony → suggest.

Lighting Designer → suggest/visualize.

Landscape Designer → guide/assist.

Decoration Scatter → automate inside player-defined rules.

Arrays → automate.

Pattern repetition → automate.

# 18. PROCEDURAL GEOMETRY

Keep the existing procedural shape work.

It remains valuable.

However, do not assume arbitrary raw voxel injection is always the preferred runtime destination.

Whenever possible:

**procedural geometry should become a planner for legitimate vanilla-compatible construction operations.**

Examples:

Wall A→B
→ planner computes placements
→ vanilla wall/foundation operations execute them.

Circle
→ planner computes positions
→ vanilla building operations place them.

→ semantic placement sequence

Raw world/voxel mutation remains an advanced fallback for features that genuinely require it.

# 21. UNDO / REDO

Undo/redo is a high-priority shared system.

Prefer semantic inverse operations where safe and available.

Examples:

place → remove
remove → restore
replace A→B → inverse replacement of affected cells
multi-placement → reverse ordered operations.

For complex terrain or voxel edits, bounded before/after diffs may still be required.

Large destructive operations should not become mature features without a credible history/undo strategy.

# 33. DEVELOPMENT PRIORITY AFTER REALIGNMENT

Do not immediately implement every planned feature.

The immediate engineering objective should be to build a **Vanilla Capability Map**.

For each desired Architect feature, determine:

1. What does the player want to accomplish?
2. Which vanilla Enshrouded system already comes closest?
3. Which KFC resources describe that system?
4. What runtime state/functions own it?
5. What parts are already PROVEN?
6. What remains unknown?
7. Can Architect reuse it directly?
8. Can it be extended?
9. Can several vanilla operations be composed?
10. What truly requires original native machinery?

For building specifically, high-value research is upstream of the final placement event:

* selected blueprint state;
* blueprint/cache object;
* decoded geometry;
* placement candidate;
* vanilla ghost;
* snap candidate/result;
* transform;
* material;
* validation;
* commit path.

Map that pipeline before creating another independent placement architecture.
