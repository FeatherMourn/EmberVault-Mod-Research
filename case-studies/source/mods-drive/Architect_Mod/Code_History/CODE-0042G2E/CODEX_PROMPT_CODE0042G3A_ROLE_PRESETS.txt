GOAL

Remove the 2 raw `.Add_Click(...)` registrations in `Render-RolePresetsPage` while making preset execution itself fail closed at the shared helper boundary.

CURRENT CANONICAL TRUTH

`admin.preset.apply` already exists and is:

- enabled=false
- evidenceStatus=`EXPERIMENTAL`
- backendAdapter=`DiagnosticsAdapter`
- backend=`NONE`
- runtimeMode=`SESSION`
- authority=`unknown`

- failureReason states that preset execution must fail closed when child actions are unavailable

Home preset buttons already bind through this canonical ActionId.

However the shared helper `Invoke-ArchitectPreset` currently loops child actions directly and always reports the preset as activated. That means a programmatic/direct call to the helper can bypass the disabled canonical preset action.

G3A must fix that shared boundary.

A. ROLE PRESET APPLY BUTTONS

Current raw source site:
`$btnApply.Add_Click(...)`

Replace with `Register-AdminActionEvent`.

ActionId:
`admin.preset.apply`

Each preset gets a stable deterministic EventId:

`f7.presets.apply.<presetId>.click`

Requirements:

- use the preset's stable `id` property;
- do not derive identity from display name or Control.Name;
- if a preset has no stable non-empty id, leave its Apply button disabled and do not register an ambiguous/generated fallback EventId;
- Page: `Presets`
- Operation: `Apply Preset <presetId>`
- LifetimeScope: PAGE
- do NOT use `AllowDisabled`

Handler may call `Invoke-ArchitectPreset $t.Tag`, but the shared helper itself must also fail closed as specified below.

Because `admin.preset.apply` is disabled, all role-preset Apply buttons must remain disabled by canonical registry gating.

B. FAIL-CLOSE `Invoke-ArchitectPreset`

`admin.preset.apply`

- no pending native command;
