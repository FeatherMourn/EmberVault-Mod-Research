## Candidate filter and transform-related code

`0x3E40D0` is an alternate placement/commit routine (seven chained `.pdata`
fragments ending at `0x3E4838`). It resolves an item (`0x3E4139`), resolves a
runtime placement record from `RSI+0xF0` (`0x3E4154`), computes min/max values
with SSE, and calls `0x3E79C0` (`0x3E4347`).

`0x3E79C0` is the strongest static snap-candidate lead, but its semantic name
is intentionally neutral. The decoded structure is:

* `RDX` is retained as `RSI`; `[RSI+0x110]` is tested and used as a candidate
  collection source (`0x3E79DC`, `0x3E7A81`).
* `RCX` is retained as `R15`; `[R15+0x00]`/`[R15+0x08]` are output storage and
  count (`0x3E7CD0..0x3E7CE7`).
* Candidate records use a `0x20` byte stride (`0x3E7DAB`). A candidate key at
  `candidate+0x08` is passed to the existing cache lookup (`0x3E7C86` and
  `0x3E7C92`).
* `comiss`, `minss`, and `maxss` comparisons (`0x3E7C3F..0x3E7C80`) perform
  containment/distance-style tests before an accepted candidate is appended.

This is structurally consistent with candidate filtering used by a snapping or
placement search stage. It does not, by itself, prove which candidate was
chosen, which KFC rule fired, or that `[RSI+0x110]` is the UI preview state.

The relationship to `0xCA90E0` is therefore proven at the data-flow level:

### v0.27 accepted collection correction

The source candidate records examined by `0x3E79C0` are 0x20 bytes, but the
caller-owned accepted collection is a distinct 0x50-byte record array. The
collection header is passed in `RCX`; `+0x00` is storage, `+0x08` count,
`+0x10` capacity, and `+0x18` a grow callback. Append addressing at
`0x3E7D5D` uses `storage + count*0x50`, and the count is incremented at
`0x3E7D99`. The accepted record contains normalized payload/dimension fields
followed by candidate-derived packed/vector values. No winner is selected in
this function; all survivors are accumulated for caller-specific processing.
See `snap_candidate_selection_static_map.json` for caller windows and exact
evidence.

The static path shows input transform fields, arithmetic, AABB/candidate
filtering, and final event construction. It does not expose a uniquely named
pre-snap field, post-snap field, or preview-update callback. Position and
orientation are demonstrably prepared before `0x3E3505`, but the exact point at
which a candidate changes them is **UNSOLVED**. A difference between two event
contexts would not alone establish that snapping occurred.

The offline KFC catalog is available (`7` configuration families and `31` real
rules), but no native link from those GUIDs to the candidate records was found.
The item-to-family mapping remains `UNSOLVED`; no SQLite dependency was added
to native code.

## Observer decision

No new observer is justified for v0.25. `0x3E79C0` is a strong static lead, but
there is no validated instruction window that safely samples a distinct
pre-placement transform without risking the known placement path. The only
runtime hook remains the existing, validated `BuildingPlaceEvent` hook. The
machine-readable map records `observerDecision.install = false` and
`FAIL_CLOSED_STATIC_ONLY`.

## Next evidence boundary

A future read-only build would need a separately validated preview update or
field-writer site, then correlate its bounded transform record with the event
context. Until such a site is proven, do not add a hook, infer a rule identity,
or attempt Architect snap control.
