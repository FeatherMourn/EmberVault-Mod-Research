==================================================
WHY THIS TASK EXISTS
==================================================

The outer F7 form is already resizable and uses a docked header/nav/body shell, but the page contents remain fixed-pixel layouts.

The current page renderers still use:
- New-Label(Text, X, Y, W, H, ...)
- New-Panel(X, Y, W, H, ...)
- New-Button(Text, X, Y, W, H, ...)
- direct .Location = Point(...)
- direct .Size = Size(...)

There are currently no TableLayoutPanel, FlowLayoutPanel, or DataGridView-based responsive page layouts in the main F7 runtime.

Most page content is built around roughly 590–700 px fixed widths. Enlarging F7 therefore enlarges the viewport while leaving the actual controls clustered in the upper-left.

The current UI smoke test resizes the window, but only verifies the outer Dock hierarchy. It does not verify that page content expands, reflows, avoids overlap, or consumes available width.

There is also a separate action-registry/testability blocker documented by CODE-0037C/D/E:
- ArchitectRuntime.ps1 initially builds a compatibility action ledger.
- It later replaces $adminCommandRegistry with runtime/admin_action_registry.json.
- The JSON registry currently contains only 20 actual actions.
- Many visible F7 mutation routes exist only in closures/capability aliases/actionFamilies, not canonical action entries.
- Register-SafeUiEvent does not receive a canonical ActionId.
- Many clickable controls have no stable ActionId -> Control binding.
- The current F7 Truthfulness & Safety suite is therefore not qualified.

FIX THIS FOUNDATION BEFORE ADDING MORE F7 FEATURES.
